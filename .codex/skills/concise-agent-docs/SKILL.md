# 高信息密度文档

## 写作

1. **只写必要信息。** 保留会影响后续 Agent 理解、判断、执行、验证或追溯的事实、决策及理由、约束、证据和遗留问题。删除无信息增量的句子；重复事实合并或引用。
2. **直接陈述。** 说清事实、结论和行动，不解释显而易见的背景，也不为假想误解预先辩护。风险、前提、未验证范围确实影响判断时，准确写明。
3. **结构服从内容。** 不为填模板设置章节，不限定篇幅；精简不能丢失关键日期、技术标识、原因、验证结果和未解决问题。

## 更新

**先检查已有内容，再修改；优先替换，不默认追加。**

1. 在原处更新状态、计划和结果，清除已失效或与新事实冲突的描述。
2. 删除已被新结论取代、无后续价值的探索、失败重试、阶段性汇报和重复验收；必要时合并为最终结论。
3. 保留仍影响后续工作的设计取舍、失败教训、验证证据和遗留问题。已有权威文档或 Git 历史的详细过程，保留入口即可。
4. 确保后续 Agent 能直接识别**最新结论及仍待处理或验证的事项**，不必从流水账中推断。

## 示例

**防御性解释**

- 冗余：用例结构已验收，但这不代表业务接口已经通过真实验证，因此不能认为测试已经全部完成。
- 精简：141 个用例结构验收通过；真实 HTTP 试跑因业务码 401 未通过，待有效鉴权。

**过程堆积**

- 冗余：首轮测试失败 → 修复 Fixture → 等待重跑 → 独立验收通过。
- 精简：独立验收通过；确定性测试 302 项，失败／错误／跳过均为 0。测试 Fixture 须提供完整依赖，不恢复生产空依赖兼容分支。

**必要的技术理由**

- 保留：外键使用 `ON DELETE RESTRICT`，避免级联删除任务历史；Outbox `aggregate_id` 不建外键，以保留文档删除后的 DELETE 事件。

# 03：编辑保存与异步边界

整理：2026-10-14。范围：普通块内容更新的前端提交与内核保存主线。证据为静态源码阅读，未做请求捕获、故障注入或磁盘写入时序观测。

## 从修改到保存

以把“学习 MySQL”改成“学习 JDBC”为例：

```text
页面显示修改
→ 前端组织 action=update、块 id、新块内容 data
→ 前端队列提交 POST /api/transactions
→ 内核事务入队
→ 后台修改内存树
→ 提交事务，写回文档 .sy
→ SQL 索引更新入队
```

编辑粒度来自块模型；普通 `update` 解析新的块 DOM，校验后替换旧节点，不是直接执行数据库 `UPDATE`。请求可以包含多个编辑操作，可类比批量业务操作；编辑事务不等同于 SQL 事务。

文件保存以文档为单位：所属文档树重新序列化为 JSON 写入 `.sy`，不是仅替换文件中的字符片段。文件写入逻辑可跳过无变化的重复写入。

## 同步、异步与确认

| 边界 | 当前正常路径 |
|---|---|
| 页面到保存请求 | 前端调度、队列和 HTTP 异步工作，界面不等待文件写完才显示文字 |
| API 到事务执行 | API 入队，后台执行；API 随后等待队列及事务提交结束再返回 |
| 后台事务内部 | 修改树、提交和调用文件写入顺序执行 |
| 文件到 SQL 索引 | 文件写入成功后安排索引更新，索引执行是另一个队列阶段 |

以 MQ 类比：内部事务结束是解除 API 等待的完成信号，HTTP 响应是请求回执，SQL 入队不是索引完成确认。这些进程内队列不能自动推导出 MQ 的持久消息、消费 ACK 或重投保障。

当前普通输入调度默认延迟为 0，连续调度可以取消尚未执行的前一次处理；输入法和特殊输入有独立分支。前端队列串行，符合条件的普通单块更新可并批，最多 32 项。内核后台每 50ms 检查事务队列；检查间隔不是操作完成时限，也不是索引更新周期。

## 失败后能确认什么

| 情况 | 含义 |
|---|---|
| 请求未到达内核 | 页面可能已显示修改，文件仍是旧内容 |
| 内核执行失败 | 按失败阶段清理事务状态并报告异常；不能假定前端自动恢复原文 |
| 写入完成但响应丢失 | 文件可能已更新，前端仍报告连接异常 |

普通编辑发送路径未见自动重发。事务错误可以通过 WebSocket 的 `txerr` 等路径报告，因此 HTTP 返回及状态码不能独自证明所有操作成功。`rollback` 主要清理事务工作状态及部分专项恢复，不应概括为跨全部文件和 SQL 的原子回滚。

断连后仅凭页面文字无法判定最后一次修改是否保存。保存结果不确定不等于已损坏数据。本轮未验证物理刷盘保证、故障频率、跨文件失败恢复及全部操作的异常语义。

## 重试与幂等

该路径的 `reqId` 用作时间戳及排序依据，未发现基于它的请求去重。覆盖同一正文不代表完整操作幂等：旧请求重试可能覆盖后续修改，历史等副作用也需考虑。

```text
请求 A：保存 MySQL；保存完成，但响应丢失
请求 B：随后保存 JDBC
若盲目重发 A：正文可能又回到 MySQL
```

固定操作 ID 去重与版本检查是可讨论的设计方式，不作为已存在的思源保障。作者是否主动接受此取舍、异常是否罕见、损失是否可接受，当前无足够依据。
